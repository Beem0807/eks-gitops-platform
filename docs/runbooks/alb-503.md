# ALB 503 Service Unavailable

## Symptoms

- HTTP clients receive `503 Service Unavailable` from the ALB
- ALB access logs show `503` with `target_status_code` of `-` (no target responded)
- CloudWatch metric `HTTPCode_ELB_5XX_Count` is elevated
- `curl -I https://<hostname>` returns `503`

## Impact

- **Critical**: All or a portion of user traffic is failing
- Service is completely unavailable if all targets are unhealthy
- Partial 503s if a subset of pods/nodes are removed from the target group

## Quick Checks

```bash
# Are the app pods running and ready?
kubectl get pods -n <namespace> -l app.kubernetes.io/name=<app>

# Are pods passing readiness probes?
kubectl describe pods -n <namespace> -l app.kubernetes.io/name=<app> \
  | grep -A 10 "Readiness\|Conditions\|Events"

# Check the Ingress and its ALB address
kubectl get ingress -n <namespace>
kubectl describe ingress <ingress-name> -n <namespace>

# AWS Load Balancer Controller logs
kubectl logs -n kube-system \
  -l app.kubernetes.io/name=aws-load-balancer-controller --tail=100

# TargetGroup health
aws elbv2 describe-target-health \
  --target-group-arn <arn> --region <region>

# Are there any ready endpoints?
kubectl get endpoints <service-name> -n <namespace>
```

## Root Causes

| Cause | How to Identify |
|---|---|
| All pods failing readiness probes | `kubectl get pods` shows `0/1 Ready`; endpoints empty |
| No healthy targets in TargetGroup | `describe-target-health` shows all `unhealthy` or `unused` |
| AWS LB Controller not running | No `ADDRESS` on Ingress; controller pod crash-looping in `kube-system` |
| Security group blocking the container port | Targets unhealthy but pods respond fine locally |
| IRSA role missing `elasticloadbalancing:*` | Controller logs show `AccessDenied` |
| Ingress annotation misconfiguration | Wrong scheme, backend-protocol, or listen-ports |
| Pod disruption during rolling deploy | Transient 503s; `kubectl rollout status` shows in progress |
| `targetPort` in Service mismatches container port | Targets registered but health check fails on wrong port |

## Fix

### Pods not ready / failing readiness probes
```bash
# Check what the readiness probe hits
kubectl describe pod <pod-name> -n <namespace> | grep -A 5 "Readiness:"

# Tail pod logs for startup errors
kubectl logs <pod-name> -n <namespace> --tail=50

# If a bad deploy caused it, rollback
kubectl rollout undo deployment <deployment-name> -n <namespace>
```

> **This platform**: readiness probe hits `/health` on the container port. The Ingress healthcheck is also set to `/health` via `alb.ingress.kubernetes.io/healthcheck-path: /health`.

### AWS LB Controller crash-looping
```bash
kubectl rollout restart deployment aws-load-balancer-controller -n kube-system
kubectl rollout status deployment aws-load-balancer-controller -n kube-system
kubectl logs -n kube-system \
  -l app.kubernetes.io/name=aws-load-balancer-controller --tail=100
```

### IRSA permissions missing
```bash
# Verify the role ARN annotation on the service account
kubectl get sa aws-load-balancer-controller -n kube-system \
  -o jsonpath='{.metadata.annotations}'

# If the IAM policy is missing actions, update the Terraform IRSA module and re-apply
# File: terraform/aws-load-balancer-controller-irsa.tf
```

> **This platform**: IRSA role name follows the pattern `<cluster-name>-aws-load-balancer-controller-irsa`. The IAM policy is fetched from the official AWS LB Controller policy URL in Terraform.

### Security group blocking traffic
```bash
# Find the container port
kubectl get svc <service-name> -n <namespace>

# Check the node security group allows inbound from the ALB security group on that port
aws ec2 describe-security-groups --group-ids <node-sg-id> --region <region>
```

### Ingress annotation issues
```bash
# Describe the ingress to see what annotations are actually applied
kubectl describe ingress <ingress-name> -n <namespace>
```

The required annotations for this platform:
```yaml
kubernetes.io/ingress.class: alb
alb.ingress.kubernetes.io/scheme: internet-facing
alb.ingress.kubernetes.io/target-type: ip
alb.ingress.kubernetes.io/backend-protocol: HTTP
alb.ingress.kubernetes.io/listen-ports: '[{"HTTP":80},{"HTTPS":443}]'
alb.ingress.kubernetes.io/ssl-redirect: "443"
alb.ingress.kubernetes.io/healthcheck-path: /health
```

> **This platform**: TLS certificates are **auto-discovered from ACM** based on the hostname declared in the `tls:` spec - there is no explicit `alb.ingress.kubernetes.io/certificate-arn` annotation. If the cert is not found, the HTTPS listener will not attach.

## Prevention

- Set `maxUnavailable: 0` on Deployments to prevent readiness gaps during rolling deploys
- PodDisruptionBudget is already in the chart (`minAvailable: 1`) - do not remove it
- Enable ALB access logging to S3 for post-incident forensics
- Alert on `aws_applicationelb_healthy_host_count < 1` via CloudWatch or cloudwatch-exporter
- Confirm `targetPort` in the Service spec matches the actual container listen port - the mismatch is silent until health checks begin
